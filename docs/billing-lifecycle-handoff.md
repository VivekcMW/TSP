## Durable generation policy and APIs

**Consumed attempt, not successful-post credits.** One unit is one bounded whole content-generation request, including its selected platforms/tones and the pipeline's existing bounded retries. Reserve and commit before any source fetch/provider call. Validation or pre-reservation cancellation consumes nothing; source failures, AI errors, timeout/cancellation after reservation and process crashes consume the unit. There are no automatic refunds/releases, preventing unlimited failed free calls. Paid attempts are still recorded even though that actual tier is unlimited. No per-token billing is invented.

- Periods use PostgreSQL `clock_timestamp()` while holding `billing:<tenant>` advisory transaction lock, shared with verify/webhook/cancel. Free periods are `[00:00 UTC, next 00:00 UTC)`; paid periods are the actual current subscription start/end (provider dates for recurring, captured-payment calendar interval for orders), never a guessed 30 days. Count every status by tenant and reservation timestamp in that period. Plan switches cannot erase same-day attempts; operation dedupe spans periods indefinitely.
- `server/services/generation-quota.ts`: `assertGenerationAdmission(tenantId)` does not consume; `reserveGeneration(scope, operationId, kind, inputHash)` atomically checks entitlement/count and inserts `started`; `finishGeneration(scope, operationId, status)` only transitions owned `started`; `runGeneration(scope, operationId, kind, input, signal, work)` handles reservation/execution/outcome; `readGenerationOperation(scope, id)` returns owned safe metadata or null.
- Canonical UUID intent, SHA256 of bounded canonical input (100 KB maximum), tenant/user/kind binding. Repeated same intent is 409 `generation_operation_consumed`; different user/kind/input is 409 `generation_intent_conflict`. Neither makes another provider call or charges another unit, including after Redis expiry. The ledger stores no source text, prompt, output or raw provider error. No result replay and no automatic tombstone deletion.
- Sync routes covered: `POST /api/ai/generate-post`, `/api/instant-review`, `/api/instant-review/selected`, `/api/instant-review/manual`, plus the deliberate local editorial fallback. Optional `requestIntent` must be a UUID; absent intent creates a fresh UUID. Response header `X-Generation-Operation-Id` identifies it, including generation errors. Callers should generate/persist an intent before sending if they need safe retry after losing the entire HTTP response.
- Queue routes: `POST /api/editorial/jobs/selected|manual` (and existing `Prefer: respond-async` aliases) require `requestIntent`. Admission rechecks entitlement/usage without consuming. Worker rechecks and reserves using that durable intent, not a transient job ID, and overrides generation/voice scope with persisted tenant/user ownership. Existing one-attempt/no-stalled-replay queue safeguards remain. At exhausted quota, a repeated enqueue may be denied even for an existing job; use known job status/result endpoints to recover instead of creating a fresh intent.
- `GET /api/generation/operations/:id`: authenticated `generation:create:own`, status polling limiter, `no-store`; foreign user/tenant/missing => 404. Safe response includes operationId, kind, status, periodStart/End, createdAt/completedAt, `consumed: true`, `policy: "consumed-attempt"`, `resultRetained: false`, and outcome (`started` becomes `in_progress_or_unknown`). A 404 is not permission to retry with a different intent after an uncertain response; retry the same intent.
- Errors: malformed intent/input 400; denied entitlement 403; duplicate/conflicting intent 409; quota exhaustion 429 with `Retry-After` to period end; persistence/unsafe-count failure 503 `generation_usage_unavailable`. No provider execution on reservation failure. Success-record failure is not relabeled AI failure; it leaves conservative `started`/unknown and blocks replay.
- `succeeded` means generation produced a valid result and durable success committed, **not** result delivery, draft save or publication. Worker publishes Redis completed/result only after that commit. A later Redis failure, client disconnect or legacy optional profile-publication update failure can lose delivery while generation remains succeeded. Results retain only the existing Redis TTL (300 seconds); metadata survives. No distributed PostgreSQL/Redis/provider transaction or automatic unknown-outcome reconciliation exists.
- Scope explicitly excludes onboarding assistance (`/api/ai/analyze-identity`, `/api/ai/select-engine`) and discovery summarization: those keep existing validation/rate limits and do not create content-generation credits. This is not a universal LLM cost budget. Any business requirement to meter those separately needs an explicit policy, not an invented paid entitlement.

## Catalog and expiry semantics

Only actual seeded `free` and `pro_monthly` keys have mappings. Unknown keys, missing/inactive catalog entries, malformed limits and missing periods never grant paid access. Price is not a tier. `/pricing` now renders actual public catalog values; static unlimited-free/introductory-price/grandfathering claims were removed there. No wider marketing-site audit is claimed.

Paid access requires `active` and a valid started period whose end is strictly in the future. Authentication alone is not payment. `pending`, `halted`, `paused`, `cancelled`, `expired`, `completed` revoke paid access. Scheduled cycle-end cancellation remains `active` until actual expiry/provider termination. Missing/inactive free catalog -> zero generation and all capabilities false. An unpaid newer checkout does not hide an existing unexpired paid period. Expiry is evaluated at read/assert time without requiring a cron job.

## HTTP contracts (billing manager permission except public catalog/entitlements)

- `GET /api/public/billing/plans`: unauthenticated active safe catalog fields, `no-store`; no private provider IDs. Includes boolean `recurringAvailable` (binding configured, **not** proof of provider plan validity). Catalog errors return 503 without fabricated prices. Existing manager-only `GET /api/billing/plans` remains.

- Existing `POST /api/billing/checkout/order` `{ planId }` response remains compatible: `orderId`, `amount`, `currency`, `keyId`, `plan`, `prefill`. A persisted tenant/customer/amount/currency/interval binding is committed before the response. This purchases **one calendar interval**, not an auto-renewal mandate. Period anchored to provider payment creation timestamp; month/year arithmetic clamps month-end, never a hardcoded 30 days.
- New `POST /api/billing/checkout/subscription` `{ planId, totalCount }` (`1..100` explicit cycles) returns `subscriptionId`, `keyId`, `plan`, `prefill`. Requires a configured `billing_plans.razorpay_plan_id` whose fetched amount/currency/period/interval exactly match the catalog. Default seeded plan has no provider ID: recurring checkout returns 409 until configured. No fake provider plan is created.
- `POST /api/billing/checkout/verify`: existing `{ razorpayOrderId, razorpayPaymentId, razorpaySignature }`, or recurring `{ razorpaySubscriptionId, razorpayPaymentId, razorpaySignature }`, exactly one checkout identifier. Recurring HMAC input is `paymentId|subscriptionId`; order HMAC remains `orderId|paymentId`. Signature alone never grants access. Owned persisted binding is looked up before fetching/recording payment. Payments must match exact IDs, stored amount/currency/customer; recurring payments additionally require a provider invoice bound to the same subscription/order/payment.
- `POST /api/billing/subscription/cancel`: invokes provider cancellation with `cancel_at_cycle_end: true`. Only a matching successful provider response permits local cancellation intent. Provider failure/ambiguous state returns a truthful error with no local success mutation/email. One-time purchases return 409 `no_recurring_subscription` (expire naturally). Repeated confirmed cancellation is idempotent.
- `GET /api/billing/entitlements` is readable by all authenticated tenant members; sensitive billing/account history remains manager-only. Billing and entitlement reads are `no-store`.
- `GET /api/billing` preserves response fields and adds `entitlements`; `currentPlan` reflects effective access, not an expired paid plan. Missing catalog returns `currentPlan: null` rather than an invented free record.

**Frontend implemented:** billing panel offers order versus recurring selection with explicit 1–100 cycles, uses server catalog identity (no client amount authority), configures Razorpay order/subscription checkout and verifies the matching returned identifier. Prices/features come from the catalog. Orders show “Access ends” and never offer provider cancellation; recurring shows “Current cycle ends”, not guaranteed renewal. Missing currentPlan shows “Unavailable”. Cancellation toast reflects provider-confirmed state, never assumes access for pending subscriptions. Verification says payment recorded, not guaranteed active access. Current-plan repurchase/same-tier switching remains disabled; no proration/upgrade contract was invented. Helpers and server-rendered views are mocked-tested; real browser/merchant Checkout acceptance remains outstanding.

## Webhook and concurrency contract

`POST /api/webhooks/razorpay` requires configured webhook secret, original `Buffer` raw body and valid HMAC. No JSON reserialization fallback. It parses the **signed raw bytes**, not mutable `req.body`. Existing `server/index.ts` JSON verify hook already captures raw bytes. Bad signatures/envelopes -> 400; missing secret -> 503. Unknown events are ignored without grants.

Supported lifecycle/payment events reconcile fetched current provider state, never replay old payload state directly. Payment-only events can resolve a recurring subscription via invoice. Provider notes are only a routing hint: the scoped persisted order/subscription and customer binding are still mandatory. Missing/unbound supported events are not acknowledged as processed; they need retry/operator reconciliation.

Supported event names: `payment.captured`, `payment.failed`, `payment.authorized`, `order.paid`, `subscription.authenticated`, `subscription.activated`, `subscription.charged`, `subscription.pending`, `subscription.halted`, `subscription.paused`, `subscription.resumed`, `subscription.cancelled`, `subscription.completed`, `subscription.expired`, `subscription.updated`.

All mutations run with tenant-local `set_config` + transaction advisory lock. Provider verification fetches happen **inside** that lock, so a stale in-flight fetch cannot commit after a newer one. Globally unique webhook receipt claims use INSERT ON CONFLICT; claim, payments, subscription updates and processed marker commit/rollback together. Duplicate event ID with a different payload hash is a conflict. Payment transitions allow failed -> captured, never captured -> failed/authorized, and no duplicate extends the same order period or adds the same payment method again. Provider renewals update the same subscription with actual `current_start/current_end`; terminal state cannot be revived by an old activation.
