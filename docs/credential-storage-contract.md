## Application behavior

- `createSocialAccount` and `updateSocialAccount` encrypt supplied access and refresh strings before SQL execution. Null clears a field; omitted/undefined refresh tokens are not rewritten. Readers continue returning stored values for existing publisher/OAuth consumers. Database write exceptions are replaced with fixed messages.
- Existing AES-256-GCM `enc:v1:<iv>.<tag>.<ciphertext>` and SHA-256 key derivation remain compatible. IVs are random (12 bytes), tags are 16 bytes. Existing envelopes must authenticate before an idempotent write; malformed/unknown versions and nested envelopes fail closed. Inputs are not mutated.
- Generic connect accepts only Dev.to/Hashnode raw access tokens, verifies using the existing real provider verifier, ignores no client-supplied identity/expiry/scopes (extra fields are rejected), then persists. Other generic providers fail closed and require their dedicated credential or existing OAuth flow. OAuth callbacks now require the session-bound durable state contract below; their pre-encrypted writes remain idempotent.
- Dedicated Mastodon, Bluesky, Telegram, Dev.to, Hashnode and Slack/Discord webhook routes verify before persistence. Upstream exceptions and SQL errors are neither echoed nor logged as raw objects in integration routes. HTTP credentials must be raw strings, not storage envelopes. Telegram/webhook verification retains its existing confirmation-message side effect.
- Refresh supports **LinkedIn and X/Twitter only**. Real endpoints, ten-second abort signals and redirect rejection; unsupported providers never fetch. X aliases normalize to Twitter and use its client configuration/Basic authentication.
- Refresh requires a persistence callback; tokens are internal callback data, never part of its public result or the HTTP response. Success means persistence completed through version CAS, not just that the provider issued credentials. Omitted refresh tokens remain untouched; rotated ones are encrypted by the repository. A positive numeric provider `expires_in` determines expiry, measured from request start; absent expiry becomes **null (unknown)**, never a fabricated hour. Invalid/expired responses fail without persistence. HTTP refresh responses use `Cache-Control: no-store`.

## P1 OAuth session binding and credential CAS

- X, Reddit and LinkedIn connection initiation retain the supplied `requireAuth` (production wiring: `requireDbUser`). The shared guard separately calls **Better Auth `auth.api.getSession` with the real request headers and `disableCookieCache: true`**, at initiation and callback. Neither `req.id`, Passport identity, a client user ID nor dev-auth bypass substitutes for a session. Local email verification is rechecked.
- Each state is versioned, provider-bound, HMAC-signed, strictly validated and expires in ten minutes. A fresh 256-bit nonce makes parallel tabs independent. Only its SHA-256 **full-state digest**, expiry, provider, tenant/user scope and domain-separated session HMAC are stored in `social_oauth_states`; no raw state, session ID, session token, PKCE verifier or provider credential is stored there. Session HMAC covers the stable Better Auth session ID plus provider/tenant/user and is never exposed in the state/redirect. Bearer-token rotation within the same session works; logging out/relogging or switching sessions does not.
- Callback authorization resolves membership and `social:connect:own` for the **signed tenant**, never silently selecting the personal tenant. Cross-tenant platform privilege is insufficient. An explicit mismatching tenant header or request context is rejected. Top-level provider redirects normally have no tenant header, so the signed tenant selects the lookup but never grants membership. Anonymous, another user, another session, removed membership, expired/malformed state and unavailable session/nonce storage fail before exchange. No raw provider/session/DB errors are logged by these OAuth handlers.
- Only after those checks does a scoped `DELETE ... WHERE tenant/user/provider/digest/session-binding AND expires_at > clock_timestamp() RETURNING` consume the state. A mismatch cannot delete it; duplicate/concurrent authorized callbacks have at most one exchange. Consumption commits **before** provider exchange, so provider/network/storage failure requires restarting the connection rather than replaying the callback. Provider cancellation/missing code does not consume the nonce; it expires normally. Expired rows for the initiating tenant/user are cleaned on subsequent initiation; dormant scopes need parent-coordinated retention maintenance if required.
- Every social-account update (including identity, target handle, active state, metadata, explicit credential backfill/rotation, and even an identical credential write) advances the server-owned `credential_version`. Inserts start at 0; callers cannot reset versions through the insert schema or repository. Conservative metadata invalidation is intentional. Existing envelope authentication/idempotence and plaintext read compatibility are unchanged.
- Refresh captures the version with the credentials **before** fetching, then atomically updates only credential fields under tenant/user/account-ID/version predicates. Reconnect B or refresh B advances the version so late refresh A cannot overwrite it. Deleting/recreating with a new account ID also fences A. CAS mismatch returns token-free HTTP 409 with a reload instruction; no fallback unconditional write, retry with stale credentials, or success response. A missing/invalid version fails before networking with a reconnect instruction.

## Keys and rotation

Active key precedence remains `WEBHOOK_ENCRYPTION_SECRET`, otherwise `BETTER_AUTH_SECRET`. Keys must contain at least 32 characters after trimming. A configured invalid active secret fails closed rather than silently switching keys. Keep the dedicated encryption key stable independently of authentication-secret changes.

Optional `WEBHOOK_ENCRYPTION_PREVIOUS_SECRETS` is a JSON array of at most three explicitly supplied previous secrets. It is not guessed, auto-populated or logged. Deploy readers accepting the old key before changing the active writer key; coordinate all processes and pause writers during cutover to avoid stranding new envelopes on old-only readers. Then run explicit rotation, validate coverage for **every tenant/user scope**, and only then remove old keys. Do not remove keys still required by backups. Envelopes have no key ID; bounded authenticated trial is intentional for v1 compatibility.

## Explicit legacy backfill / rotation (operator coordinated)

**Encryption alone required no SQL/schema migration; migration 0031 was not created or applied. The later P1 nonce/CAS work requires parent-coordinated 0037 above.** Existing text columns hold envelopes. Historical plaintext is not automatically rewritten on reads, boot, deployment or metadata edits. Encryption does not establish that old credentials were provider-verified; reconnect legacy/untrusted accounts through a verified flow where needed.

`script/migrate-social-credentials.ts` is a standalone `tsx` entry point. It does not load dotenv. Supply `DATABASE_URL` and keys through an approved environment/secret manager, never command arguments or copied logs. Use the tenant-restricted runtime database role, not the owner role.

Required arguments: `--tenant=<tenant-id>`, `--user=<user-id>`, `--confirm-database=<exact-database-name>`. Optional `--limit=<1..500>` defaults to 100; `--after=<last-committed-id>` resumes a scope. **Dry-run is default**; only `--apply` writes. Add `--rotate` to explicitly re-encrypt existing envelopes with the active key as well as backfilling plaintext.

1. Parent/operator confirms the target, backup/recovery plan, keys and all tenant/user scopes. No production maintenance is authorized by these code changes.
2. Dry-run from the beginning of each scope, paging with `nextAfterId` until `done`. Output contains only counts, dry-run status, cursor and completion state. Dry-run still uses bounded row locks and authenticates envelopes; it can block writers briefly.
3. After approval, start apply **from the beginning**, not from the final dry-run cursor. Save each successful batch's `nextAfterId` externally. Keep scope and rotation options with that checkpoint. A failed batch returns no new checkpoint; restart from the last committed one.
4. Each batch locks rows in stable ID order inside one scoped transaction. Both credential fields are updated under the same row lock, so it cannot overwrite a concurrently refreshed token read before the lock. Corrupt/unknown envelopes abort the batch, with fixed secret-free errors. Repair/reconnect affected rows explicitly; no silent skipping.
5. Repeat dry-run from the beginning after backfill (`--rotate` omitted) to confirm zero plaintext candidates. Replays of normal backfill are idempotent; rotation replays are safe but produce fresh ciphertext. During rotation, finish all checkpoints and verify old-key removal in a controlled follow-up; candidate counts alone do not identify which key encrypted a row.

New inserts behind an ID cursor are covered by the repository's new-write encryption. Coordinate older app processes/direct SQL writers separately. Historical nested envelopes intentionally require explicit investigation/reconnection rather than guessing multiple decryption layers. Database backups/log retention containing old plaintext need their own security policy.
